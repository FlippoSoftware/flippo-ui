# @flippo-software/core-components — notes for agents

Framework-agnostic state machines for every Flippo UI component: state, transitions, ARIA/props, keyboard and pointer
interactions, focus management, dismissal, positioning (on `@floating-ui/dom`). Adapters render: React in
`../headless-components`, custom elements in `../web-components`. Behaviour belongs here, not in an adapter.

`README.md` documents the entry points, the machine shape and the adapter contract; keep it current.

## Layout

```
src/components/<name>/        one folder per part: root/, trigger/, popup/, positioner/, item/…, plus store/, utils/
                              <Part>Machine.ts, <Part>DataAttributes.ts, *CssVars.ts, *StateAttributesMapping.ts
                              <Name>Machines.test.ts / <Name>Store.test.ts at the component root
src/components/<name>/index.ts  the component's entry point (explicit exports)
src/lib/                      shared helpers + attributes/ dom/ events/ patterns/ popup/ positioning/ props/ store/ timers/
src/packages/floating-ui/     our fork of the Floating UI interactions on @floating-ui/dom (FocusManager, Dismiss…)
test/                         architecture.test.ts (no React, imports in Node), ssr.test.ts, reconnect.test.ts, utils/
```

Imports between areas use aliases (`~@lib/*`, `~@components/*`, `~@attributes/*`, `~@dom/*`, `~@events/*`, `~@popup/*`,
`~@positioning/*`, `~@props/*`, `~@timers/*`, `~@packages/*`, …; mirrored in `aliases.ts` for Vitest). Files of the
same component import each other relatively. Every component and lib folder is an entry point (`tsdown.config.ts`
`COMPONENTS` / `LIB_MODULES`; `package.json` `exports` generated by tsdown).

## The machine shape (follow it exactly)

- `class XMachine extends Connectable`. Constructor: no side effects (SSR, discarded renders). `onConnect()` starts
  listeners/subscriptions/timers (`addCleanup`, `connectChild(child)`); `connect()` returns `disconnect`; instances
  reconnect (StrictMode).
- Options live in a per-machine `OptionsStore` (`private readonly optionsStore = new OptionsStore<XOptions>(…)` with
  `options` getter/setter) so computed values and effects track them key by key.
- `setOptions(options)` runs on every render: its body is wrapped in `untracked(() => …)`, it only updates state,
  and **never calls user callbacks**. Side effects of option changes go to `afterCommit()`.
- State derivation: `effect(() => this.sync())` in `onConnect` for multi-store syncing; per-item `computed` for list
  items (e.g. `isHighlighted`).
- `getState()`, `static attrs(state)` (data attributes via `getStyleHookProps` + a mapping file), `getXProps(elementProps)`
  returning props compatible with `mergeProps` (React-shaped: `onClick`, `tabIndex`, style objects), element setters
  as arrow functions (`setElement = (element) => …`).
- Controlled values through `ComponentStore.syncControlledValue`; user callbacks get `ChangeEventDetails`
  (`createChangeEventDetails(REASONS.x, event)`, `cancel()`).
- No `react`/`react-dom`, no module-level `window`/`document` (enforced by Biome and `test/architecture.test.ts`).

## Tests

Vitest + happy-dom. Wrap machines with `connected(machine)` from `test/utils/connected.ts` (`~@test/*`), which
disconnects at the end of the test. Test behaviour through props handlers and DOM events, plus SSR (`setOptions`
without DOM) and reconnect where relevant. Coverage threshold is a ratchet.

## Commands and consumers

`pnpm lint:check`, `pnpm typecheck`, `pnpm test`, `pnpm build`. `headless-components` and `web-components` use the
built `dist/` via `link:../core`: run `pnpm build` after every change, then their tests (`pnpm test` there).
Depends on `../store` via `link:`. Pitfall: the shared tsconfig enables `incremental`; if `tsc` looks stale, run
`tsc --noEmit --incremental false --composite false`.

Never commit, push or publish unless asked.
